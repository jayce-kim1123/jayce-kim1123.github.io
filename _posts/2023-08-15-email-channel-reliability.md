이메일을 문의 채널로 연동하는 기능에서 한 주 사이에 서로 다른 문제 두 개를 만났다. 하나는 외부 API의 숨은 제약, 다른 하나는 사람이 입력한 값이 프로토콜을 깨는 경우였다.

## 하루 2000건 - 눈에 안 보이던 API 쿼터

Gmail API 연동으로 이메일 채널을 쓰던 한 고객사에서 특정 시점 이후로 티켓이 생성되지 않는다는 문의가 들어왔다. 원인은 Gmail API의 일일 처리 한도였다. 하루 처리량이 2000건을 넘어가면 그 이후 메일은 조용히 처리되지 않았다. 에러가 나는 것도 아니고 그냥 "안 만들어지는" 상태라 발견이 늦었다.

이 시점에 Gmail API 방식으로 연동된 테넌트가 해당 고객사 하나뿐이어서 다른 테넌트에는 영향이 없었다. 근본적인 해결책으로는 그 고객사의 연동 방식을 API 방식에서 IMAP 방식으로 전환하기로 했다. 그리고 별개로, Gmail이 보내는 push 알림에 대해 우리 서버가 항상 200을 반환하도록 수정했다. 실패 응답을 보내면 Gmail이 같은 알림을 계속 재시도하는데, 처리에 실패한 메일이 있을 때마다 재시도가 쌓이면 오히려 상황을 더 꼬이게 만들 수 있었다. 실패는 우리 쪽 로그로 남기고, 외부에는 일단 수신 확인만 보내는 방식으로 바꿨다.

## 이메일 헤더에 꺾쇠괄호가 들어가면 파싱이 깨진다

두 번째는 SMTP 발송 쪽이었다. 발신자 표시 이름에 브랜드명을 그대로 넣고 있었는데, 어떤 브랜드명에 꺾쇠괄호(`<`, `>`)가 포함되어 있었다. 이메일의 발신자 필드는 보통 `이름 <주소>` 형식인데, 이름 부분에 이미 꺾쇠괄호가 들어가 있으면 파싱 로직이 실제 이메일 주소를 엉뚱한 위치에서 잘라내는 문제가 생겼다. 이름에 괄호가 섞이면서 주소 경계 자체가 어그러진 것이다.

같은 시기에 SSL 관련 에러도 있었는데, 이건 고객사 쪽 SMTP 포트 설정 문제로 포트를 바꾸는 것으로 해결됐다. 반면 꺾쇠괄호 문제는 우리 쪽에서 막아야 하는 종류였다. 발신자 이름으로 쓰일 값에 이메일 헤더 문법과 충돌하는 문자가 들어가지 않도록 입력 단계에서 제한하는 방향으로 정리했다.

## 남은 생각

두 문제 모두 "정상적인 상황을 가정한 설계"가 실제 운영 환경과 부딪힌 경우였다. API 쿼터는 처음 연동할 때는 신경 쓸 일이 없다가 트래픽이 늘어난 뒤에야 존재가 드러났고, 이름 파싱 문제는 "발신자 이름에 이메일 헤더 문법을 깨는 문자가 들어갈 수 있다"는 걸 애초에 고려하지 않아서 생겼다. 외부 서비스와 연동하는 코드는 그 외부 서비스의 제약(쿼터, 프로토콜 규격)까지 우리 쪽 입력 검증 범위에 포함시켜야 한다는 걸 이 두 건에서 같이 배웠다.
