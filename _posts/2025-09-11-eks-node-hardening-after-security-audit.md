외부 보안 점검을 받고 나서 후속 조치 항목이 여러 개 떨어졌다. TLS 1.0/1.1 사용 중지, nginx 에러 핸들링 정리, 세션 유지 시간 단축, 비밀번호 재설정 페이지 reCAPTCHA 적용 같은 것들과 함께, EKS 워커 노드용 EC2 인스턴스 보안 강화도 그중 하나였다. 항목 자체는 흔한 체크리스트였는데, EKS 노드 쪽은 다른 항목들과 성격이 좀 달랐다.

## 대부분은 한 번 고치면 끝나는 것들

nginx 서버 헤더 노출 방지, 에러 코드 대신 200 OK로 오버라이딩해서 내부 정보를 숨기는 것, ALB 응답에서 서버 파라미터 제거, 세션 유지 시간을 줄이는 것 - 이런 항목들은 설정 파일이나 미들웨어를 한 번 고치면 그걸로 끝이었다. 배포하고 나면 그 상태가 계속 유지된다.

## EKS 노드는 그렇지 않았다

EC2 레벨의 보안 설정(예: 특정 커널 파라미터, 에이전트 설치 여부 같은 것들)은 인스턴스에 직접 적용하는 방식으로 처리하면, AMI를 교체하거나 노드 그룹의 EKS/커널 버전을 올릴 때 그 설정이 초기화된다. 새 AMI로 노드가 재생성되면 우리가 수동으로 걸어둔 설정은 다시 원래 상태로 돌아간다는 뜻이다.

이 문제를 풀기 위해 AWS Systems Manager의 상태 관리(State Manager) 기능을 썼다. 개별 인스턴스에 설정을 한 번 적용하고 끝내는 대신, State Manager 연결(association)로 설정을 등록해두면 새로 뜨는 노드에도 동일한 설정이 주기적으로 재적용된다. AMI 교체나 버전 업그레이드로 노드가 새로 생성되는 상황을 아예 전제로 깔고, 설정을 "한 번 적용"이 아니라 "계속 유지되도록" 만드는 방식으로 접근을 바꾼 셈이다.

## 남은 생각

보안 점검 후속 조치 리스트를 받으면 각 항목을 비슷한 무게로 처리하기 쉬운데, 실제로 해보니 무게가 다 달랐다. 애플리케이션 레벨 설정은 배포 한 번으로 영구히 반영되지만, 인프라 레벨 설정 중에서도 노드처럼 주기적으로 교체되는 리소스에 건 설정은 "한 번 맞고 끝"이 아니라 "교체될 때마다 다시 맞아야 하는" 성격을 가진다. 이 차이를 미리 인지하지 못했으면, 다음 AMI 업데이트 때 조용히 보안 설정이 풀린 채로 운영됐을 수도 있었다.
