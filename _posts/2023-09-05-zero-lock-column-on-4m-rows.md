문의(티켓) 데이터 검색이 DB 쿼리 하나로 굴러가고 있었다. 티켓 번호, 제목, 본문, 답변 내용, 태그, 문의자 이메일/이름/고객ID/회사 정보까지 - 검색 범위는 넓은데 그걸 전부 DB 쿼리로 커버하려니 느렸다. 검색 엔진을 따로 두기로 했고, Elasticsearch를 골랐다.

## 왜 Elasticsearch였나

몇 가지가 겹쳤다.

- **비용**: 인스턴스 비용을 빼면 사실상 무료다. 라이선스 비용이 드는 상용 검색 솔루션 대비 도입 장벽이 낮았다.
- **Kibana**: 검색 엔진만 놓고 끝나는 게 아니라, 별도 도구 없이 바로 데이터를 들여다보고 대시보드를 만들 수 있는 Kibana가 딸려온다는 게 컸다.
- **ELK 스택으로의 확장성**: 지금 당장은 검색만 쓰지만, 나중에 Logstash나 Beats로 로그 수집 파이프라인까지 넓힐 수 있는 생태계라는 점도 고려했다. 검색 엔진 하나만 보고 고른 게 아니라, 이후 관측 가능성(observability) 쪽으로 넓혀갈 여지를 같이 산 셈이다.

## 적용하면서 만난 문제들

### 로컬 개발 환경부터 막혔다

`fasttext`, `pycrypto`, `mysqlclient` 설치가 팀 개발 환경(리눅스)에서 계속 실패했다. 로컬(맥)에서는 같은 `requirements`로 멀쩡히 설치되는데 리눅스 환경에서만 오류가 났다. 결국 pip 버전을 명시적으로 고정하고, 일부 패키지는 리눅스 배포판에 맞는 사전 빌드 패키지로 바꿔서 해결했다. 사소해 보이지만, 팀원 전체가 검색 기능 개발에 참여하려면 이 로컬 환경 문제부터 풀어야 했다.

### 클러스터를 얼마나 크게 잡아야 하는가

처음 겪는 문제였다. 개발 환경에서 티켓 3,500건을 인덱싱했을 때 클러스터 용량이 20MB 나왔다. 이 비율로 단순 계산하면 30GB 용량으로 티켓 500만 건 이상을 저장할 수 있다는 계산이 나왔고, 이 수치를 기준으로 스테이징/라이브 클러스터 사이즈를 잡았다. 호스팅은 GCP와 AWS를 비교해서(GCP 월 $35.35 vs AWS 월 $29.16) AWS로 결정했다. 가용성 구성도 환경별로 다르게 뒀다. 스테이징은 데이터가 날아가도 상관없어서 1-zone으로, 라이브는 데이터 유실을 막기 위해 2-zone으로 구성했다.

### is_indexed 컬럼 하나가 제일 오래 걸렸다

인덱싱이 끝난 데이터인지 구분하려고 원본 테이블에 `is_indexed` 컬럼을 추가해야 했는데, 이 테이블이 수백만 건짜리 운영 테이블이었다. 스테이징에서 테스트해보니 수십만 건 규모에서도 컬럼 추가에 분 단위가 걸렸고, 테이블에는 이미 풀텍스트 인덱스가 걸려 있었고, 환경마다 MariaDB 버전도 미묘하게 달랐다.

- `ALGORITHM=INPLACE, LOCK=NONE` → 풀텍스트 인덱스가 있으면 거부됨
- `ALGORITHM=INPLACE, LOCK=SHARED` → 쓰기가 막힘, 운영 중인 테이블엔 못 씀
- `ALGORITHM=INSTANT` → 우리 MariaDB 버전엔 없는 기능
- gh-ost → 외래키 제약 때문에 못 씀

남은 건 pt-osc였다. 이번에 처음 써봤다. 그림자 테이블을 만들고 트리거로 변경분을 복사하다가, 준비되면 테이블 이름을 스왑하는 방식이다. 스테이징에서는 스왑까지 잘 됐는데, 운영 기준으로 계획을 세우다 보니 두 가지가 걸렸다. 레플리카 지연이 안정적으로 잡히지 않았고, 트리거 기반 복사가 이미 부하가 있는 쓰기 DB에 부담을 얹었다. 결국 pt-osc를 운영 DB에 직접 돌리는 대신 AWS RDS 블루/그린 배포로 우회했다. 운영 DB의 복제본(그린)에서 스키마 변경을 끝내고 준비되면 트래픽을 전환하는 방식이라, 쓰기 자원도 레플리카 지연도 신경 쓸 필요가 없었다. 결과적으로 수백만 건 규모 테이블에 다운타임도 락도 없이 컬럼을 추가했다.

## 남은 생각

돌아보면 이 첫 도입에서 만든 구조와 판단들에는 허점이 꽤 있었다. 인덱싱 배치가 어떤 DB(원본이냐 레플리카냐)에서 데이터를 읽는지, 인덱스를 엔티티별로 어떻게 나눌지 같은 것들을 이때는 깊이 고민하지 못한 채로 일단 굴러가게만 만들었다. 지금도 이어지고 있는 검색 고도화 작업의 개선 항목 대부분이 사실 이때 미처 다듬지 못한 지점들에서 나온다. 처음 도입할 때는 "일단 되게 만드는 것"이 우선이었고, 그 판단 자체는 맞았다고 생각한다. 다만 그 판단들이 이후 어디서 다시 발목을 잡는지는, 시간이 좀 지나고 나서야 보이는 경우가 많았다.
