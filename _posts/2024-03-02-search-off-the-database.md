문의 데이터 검색에 Elasticsearch를 도입한 다음 차례는 지식창고(FAQ) 문서 검색이었다. 게시글·공지사항·이벤트 문서가 쌓이면서 DB `LIKE` 쿼리 기반 검색이 눈에 띄게 느려졌고, 이번에도 검색 엔진을 붙이기로 했다.

## 골치 아팠던 건 엔티티 3개, 테이블 2개

이번 프로젝트의 진짜 난이도는 검색엔진 자체가 아니라 데이터 구조에 있었다. 검색 대상은 아티클, 공지사항, 이벤트 세 종류였는데, 실제 DB에는 이 셋이 두 개의 테이블에 나뉘어 들어가 있었다. 아티클은 자기 테이블이 따로 있었고, 공지사항과 이벤트는 하나의 테이블에 타입 구분 컬럼으로 같이 담겨 있었다.

그런데 검색은 세 엔티티를 각각 다른 성격으로 다뤄야 했다. 정렬 기준도, 노출 필드도, 검색 가중치도 서로 달랐다. 그래서 인덱스는 테이블 구조를 따라 2개가 아니라, 엔티티 기준으로 3개를 만들기로 했다. 공지사항과 이벤트가 한 테이블에 있다고 해서 인덱스까지 하나로 합치면, 검색 결과 정렬이나 필드 노출에서 계속 예외 처리를 해야 했을 것이다. 처음엔 테이블 구조에 맞춰 인덱스도 2개로 시작했다가, 공지사항과 이벤트를 분리하지 않으면 계속 발목을 잡는다는 걸 깨닫고 인덱스를 3개로 다시 나눴다. 이 과정에서 인덱싱 로직에 쓰던 Enum 클래스도 같이 손봐야 했다.

## 지난번 교훈을 미리 적용한 것들

문의 데이터 검색을 만들 때 배운 게 있어서, 이번엔 같은 실수를 피하려고 처음부터 챙긴 것들이 있다.

- **인덱싱은 시작부터 쓰기 DB(RW)에서**: 지난번엔 레플리카 지연 때문에 막 생성된 데이터가 인덱스에서 조용히 누락되는 문제를 겪었다. 이번엔 인덱싱 관련 쿼리를 처음부터 RW DB로 잡아서 같은 문제를 피했다.
- **전환 기간 동안 기존 검색 로직 유지**: 인덱싱이 끝나기 전까지는 예전 DB 기반 검색 로직을 걷어내지 않고 그대로 살려뒀다. 신규 검색 로직으로 완전히 전환하기 전에 문제가 생겨도 곧바로 되돌릴 수 있게 하려는 안전장치였다.

## 그래도 새로 만난 문제들

- 인덱스를 엔티티별로 나누다 보니, 특정 엔티티(공지사항 또는 이벤트)에 인덱싱할 데이터가 하나도 없는 경우를 상정하지 않은 코드가 있어서 `KeyError`가 났다.
- 객체 하나만 다시 인덱싱할 때 `is_indexed` 플래그가 갱신되지 않는 버그가 있었다. `ValuesQuerySet`에 `update()`를 잘못 태워서 실제 인스턴스 상태와 DB 값이 어긋난 케이스였다.
- 전환 이후에도 검색어 최대 길이(60자→30자), 최대 결과 개수(10개→25개) 같은 값은 실제 사용 로그를 보고서야 조정했다. 처음 잡은 값은 대부분 추측치였다.

## 남은 생각

지난번 도입에서 얻은 교훈 중 일부(레플리카 대신 RW, 전환 기간 동안 기존 로직 유지)는 이번엔 문제가 아니라 처음부터 세팅으로 들어갔다. 반면 데이터 구조(엔티티 개수와 테이블 개수가 안 맞는 것)에서 오는 문제는 지난번엔 아예 없던 종류라 그대로 부딪혀야 했다. 같은 기술을 두 번째로 도입한다고 해서 첫 번째보다 무조건 쉬운 건 아니었다. 반복되는 실수는 확실히 줄었지만, 데이터 구조가 다르면 그만큼 새로운 문제가 나온다는 걸 이번에 알았다.
