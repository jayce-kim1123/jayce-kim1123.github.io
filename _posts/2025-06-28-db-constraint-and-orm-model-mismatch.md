특정 엔티티(브랜드 성격의 상위 조직 단위) 삭제 기능이 갑자기 동작하지 않는다는 버그 리포트가 들어왔다. 삭제를 시도하면 응답이 안 오고 서버가 멎어버리는 증상이었다. 원인을 추적하다가 완전히 다른 두 가지 문제가 겹쳐 있었다는 걸 알게 됐다.

## 첫 번째: FieldTracker의 무한 재귀

`django-model-utils`의 `FieldTracker`를 쓰고 있었는데, 삭제 시 Django의 `Collector.collect()`가 연관된 객체들을 순회하는 과정에서 `FieldTracker`의 내부 동작(`get_field_value` → `getattr()`)이 무한 재귀에 빠지는 걸 발견했다.

원인은 트래커가 전체 필드를 추적하도록 설정돼 있었기 때문이다.

```python
# 무한 재귀 발생
tracker = FieldTracker()
```

외래키가 걸린 필드를 추적 대상에 포함시키면, `FieldTracker`가 `getattr()`로 그 필드에 접근할 때 이걸 "인스턴스 접근"으로 판단해서 다시 추적 로직을 타고, 그 안에서 또 `getattr()`을 호출하는 식으로 재귀가 끊이지 않는다. 삭제 대상 필드를 명시적으로 좁히고, 외래키 필드는 인스턴스가 아니라 `_id` 형태로 추적하도록 바꿔서 해결했다.

```python
# 정상 동작
tracker = FieldTracker(fields=["category_id", ...])
```

## 두 번째: 테이블과 모델의 on_delete가 어긋나 있었다

무한 재귀를 고치고 나서도 삭제가 실제로는 실패하는 케이스가 남아있었다. 원인을 더 파보니, DB 테이블에 걸린 외래키 제약조건의 `ON DELETE` 동작과 Django 모델에 선언된 `on_delete` 옵션이 서로 다르게 설정돼 있었다. 모델 코드만 보면 `CASCADE`로 삭제되도록 짜여 있는데, 실제 테이블의 제약조건은 다른 정책(`RESTRICT`류)으로 걸려 있어서, ORM이 삭제를 시도하는 순간 DB 레벨에서 거부당하는 상황이었다.

이건 코드 리뷰로는 절대 못 잡는 종류의 버그다. 모델 정의만 보면 문제가 없어 보이기 때문이다. 실제 테이블의 제약조건을 조회해서 모델 코드와 하나하나 대조하는 작업이 필요했고, 어긋난 부분을 찾아 마이그레이션으로 동기화했다.

## 남은 생각

Django ORM은 모델에 선언한 `on_delete`가 진실이라고 믿게 만든다. 하지만 실제 삭제 동작을 결정하는 건 마이그레이션 히스토리를 거쳐 DB에 실제로 반영된 제약조건이다. 둘은 원래 같아야 하지만, 수동으로 스키마를 만졌거나 마이그레이션이 꼬인 이력이 있으면 조용히 벌어진다. 그리고 벌어진 상태로도 대부분의 케이스에서는 아무 문제 없이 동작하기 때문에, 삭제처럼 특정 방향의 연쇄 동작이 실제로 트리거되기 전까지는 드러나지 않는다. 이번 일로 "모델 코드가 스키마의 진실이다"라는 가정을 의심하게 됐고, 이후로는 중요한 테이블은 주기적으로 실제 제약조건과 모델 정의를 대조해보는 습관이 생겼다.
