EKS 워커 노드 kubelet 버전 마이그레이션 작업 중에 전역 서비스 장애가 났다. 작업 자체는 흔히 하던 버전 업그레이드였는데, 예상 못 한 곳에서 문제가 터졌다.

## 무슨 일이 있었나

새벽 시간대에 kubelet 버전 마이그레이션을 시작했다. 몇 분 지나지 않아 내부 운영 콘솔과 알림 서버 등 일부 서비스가 지연되거나 접근 불가 상태가 됐고, 곧이어 일부 서비스는 지연, 나머지는 접근 자체가 안 되는 상황으로 번졌다.

- 00:05 - kubelet 버전 마이그레이션 작업 시작
- 00:10 - 일부 서비스 지연 또는 접근 불가
- 00:15 - 장애 감지 및 원인 파악 시작
- 00:19 - 일부 서비스는 지연, 나머지 서비스는 접근 불가
- 00:21 - 원인 파악 완료
- 00:26 - 조치 시행 후 정상화 테스트, 장애 상황 해결

## 원인 - 컨트롤러가 VPC를 못 찾았다

kube-system 네임스페이스의 `aws-load-balancer-controller`가 워커 노드 버전 마이그레이션 도중 재시작됐는데, 이 과정에서 VPC 정보를 자동으로 인식하지 못했다. 보통 이 컨트롤러는 인스턴스 메타데이터를 통해 자신이 속한 VPC와 리전을 알아내는데, 마이그레이션 작업 중의 노드 상태 변화가 이 자동 감지를 방해한 것으로 보인다. VPC를 못 찾은 컨트롤러는 로드밸런서 리소스를 제대로 관리하지 못했고, 그 결과가 전역 서비스 장애로 이어졌다.

조치는 `kubectl -n kube-system edit deployment aws-load-balancer-controller`로 deployment를 직접 수정해서, 컨트롤러 실행 인자에 리전과 VPC ID를 명시적으로 넣어주는 것이었다.

```
args:
  ...
  --aws-region=ap-northeast-2
  --aws-vpc-id=vpc-xxxxxxxx
```

자동 감지에 기대지 않고 값을 하드코딩으로 박아주자 곧바로 정상화됐다.

## 재발 방지 - 노드 버전 마이그레이션 절차를 다시 짰다

EKS 컨트롤 플레인 버전 마이그레이션은 AWS 관리 콘솔에서 진행해도 문제가 없었다. 문제는 kubelet/노드 버전 마이그레이션 쪽이었고, 이걸 관리 콘솔에서 그대로 진행하면 같은 문제가 반복될 걸로 판단해서 절차를 다시 정했다.

1. 새 노드 그룹을 추가한다 (taint를 걸어서 기존 워크로드가 바로 옮겨가지 않도록)
2. 새 노드 그룹만 버전을 마이그레이션한다
3. kube-system 네임스페이스의 파드들이 정상 동작하는지 확인한다
4. 기존 노드 그룹의 노드들을 cordon 처리한다
5. 새 노드 그룹의 taint를 제거한다
6. 파드를 하나씩 rollout restart 하면서 상태를 확인한다
7. 기존 노드 그룹을 삭제한다

핵심은 "새 버전의 노드에서 kube-system 핵심 컨트롤러들이 정상 동작하는지"를 전체 트래픽을 옮기기 전에 검증하는 단계를 넣은 것이다. 이전 절차는 기존 노드 그룹을 그 자리에서 바로 업그레이드하는 방식이라, 컨트롤러가 재시작 후 제대로 뜨지 못하면 그 즉시 전역 장애로 번지는 구조였다.

## 남은 생각

버전을 하나 올리는 작업이 왜 위험한지는 대개 "무엇이 바뀌는지"보다 "그 변화가 어떤 자동화 로직의 전제를 깨는지"에서 나온다. 이번 경우엔 노드가 재시작되는 그 짧은 순간에 컨트롤러의 VPC 자동 감지 로직이 흔들렸다. 새 노드 그룹을 별도로 띄워서 kube-system 컴포넌트가 새 버전에서도 정상 동작하는지 먼저 확인하는 절차를 넣은 이유가 이거다. 기존 노드를 그 자리에서 바꾸는 방식은 "실패하면 전체가 같이 죽는" 구조이고, 새 노드 그룹을 옆에 띄워서 검증 후 전환하는 방식은 실패해도 기존 노드 그룹이 살아있어 피해가 국한된다. 인프라 버전 업그레이드는 롤백 가능한 경로를 항상 열어둔 채로 진행해야 한다는 걸 이번에 제대로 배웠다.
